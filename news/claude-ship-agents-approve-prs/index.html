The Dispatch

Claude Ship can approve your pull requests, and its docs explain how that goes wrong

Anthropic's new set of GitHub agents reviews, fixes and can sign off on code changes. Here is what each agent does, what it costs, and the policy settings that decide whether a person still looks before anything merges.

AI toolsNovember 25, 20265 min read

Anthropic launched Claude Ship on 23 November, a set of agents that take a GitHub pull request from first review to an approval decision, and in the right configuration can approve it without a second person ever looking. If your team is on a Team or Enterprise plan and someone is about to switch it on, read the policy section below first.

Coding agents now write code faster than people can review it, so the queue of open pull requests has become the slow part. Anthropic says Claude writes most of the code on its own Claude Code team, and it built Claude Ship to make everything after the pull request move at the same pace.

Three agents, each with a narrow job

Claude Ship bundles three pieces, adopted one at a time, one repository at a time.

Code Review is the one that has been around since March and is now generally available. It reads a change alongside the code around it, runs several agents that check each other's findings, and posts inline comments ranked by severity. Each repository can pick a Quick, Standard or Deep review level, and a REVIEW.md file tunes what it cares about.

PR Steward, in beta, is the cleanup crew. It works on failing CI checks, merge conflicts and review comments from people and from bots, Code Review included, and pushes commits with its fixes. After each push it leaves a comment saying what it changed and how to undo it. You can steer it with @claude or halt it with @claude stop. By design it never approves or merges anything.

Claude Approvals, also in beta, is the new idea. It is a GitHub check driven by a policy file you commit at .claude/approvals.yml. Rules in that file match paths and set how many people must approve, and whether Claude itself may post an approving review. Billing code might need two humans; test fixtures might need one person once Code Review passes. Rules can also read facts about the pull request, such as lines changed, and the answers of classifiers: model judgments on questions like how risky a change looks.

There is a local version too. Developers can run /ship in Claude Code or the desktop app to push a change, open the pull request, review it and work through feedback and failing checks. Merge rights follow their GitHub permissions.

The settings that let code merge unseen

Credit where it is due: Anthropic's documentation is unusually blunt. A full page lists the ways a pull request can merge with nobody but its author looking, or with no person at all if a bot wrote it. The short version:

  • The check is not required. Claude Approvals blocks a merge only if you make it a required check in GitHub's branch rules. In observe mode it normally blocks nothing.
  • The policy asks for nobody else. The author can fill a seat, so seats: 1 means no second pair of eyes. With seats: 0, a bot's pull request can merge untouched.
  • Claude approves without a review. A rule set to claude: approves does not start a Code Review by itself, so Claude can approve a change nothing has examined.
  • Bots pass as people. A machine user, meaning a GitHub account driven by a script or agent, can count as a human.
  • The pull request steers the classifier. The docs warn that an author's text can steer a classifier's answer, and if a rule reads that answer, a steered answer can lower what the change needs. That is prompt injection, in the vendor's own threat model.
  • Auto-merge and merge queues. Combine either with a policy that never asks for a person, and a change can merge without anyone acting.

The approval policy is now code, and like any code it does exactly what you wrote, not what you meant.

How to try it without regretting it

  1. Start with Code Review on one repository and set a monthly spend limit in Organization settings, Claude Ship. You need the Owner role.
  2. Add PR Steward in Manual mode, so it starts only when someone comments @claude steward. It has no spend limit until you set one.
  3. Add Approvals in observe mode (mode: observe in the policy file) and watch what it would have decided for a couple of weeks.
  4. Before enforcing, add a floor rule. The docs give one: on every path, require one seat filled from: [humans, "!pr/authors"], and add your CI bot's login with a ! to keep it out. Then make the Claude Approvals check required.
  5. Turn on stale-review dismissal in GitHub, because Claude's approval is attached to one commit, and require pull requests on the default branch, since direct pushes get no check at all.
  6. Keep claude/code_review under advisory in your rules. Adding a policy file can otherwise quietly stop automatic reviews.

Watch the bill. Everything is charged by tokens against your organization's usage credits, separate from plan usage, and observe mode is billed too. Turning off usage credits does not stop an agent that is switched on; you have to turn the agents off, Approvals first. Eligible Enterprise organizations can claim at least $10,000 in credits by 15 January 2027, valid for 30 days. Claude Ship is not available with Zero Data Retention, the HIPAA configuration or customer-managed encryption keys, and it supports GitHub only.

What Anthropic says it got out of it

On its own Claude Code team, Anthropic says merged pull requests more than doubled from June to September while the share of reverted changes fell by more than 40%. Those are the company's numbers and nobody has checked them independently. Decrypt points to research suggesting models are slightly worse at finding flaws in AI-written code than in human-written code, which is the uncomfortable question under the whole product: a model reviewing a model's work may share its blind spots. Anthropic's product page carries its own warning that Claude Ship "may miss bugs, security vulnerabilities, or other issues."

The bigger picture

Code review was never only about catching bugs. It is how a second person learns what changed and agrees to own it. Claude Ship turns that agreement into a YAML file, which is honest: rubber-stamp approvals on routine changes are already common, and writing the rules down is an improvement. The risk is the other direction, where a policy written for documentation fixes slowly widens until the only reader of a change to the payment code was the model that wrote it.
