LiteLLM's guardrail tester is under attack, its fourth exploited bug of 2026

CISA says attackers are using a sandbox escape in the popular LLM gateway's custom guardrail endpoint. Here is what the bug does, why an admin-only flaw still matters, and the one upgrade that closes all four of this year's exploited holes.

CyberNovember 20, 20265 min read

CISA added a LiteLLM sandbox escape to its list of actively exploited vulnerabilities on Wednesday, and it is the fourth LiteLLM bug to land there this year. If you run LiteLLM as the gateway in front of your model providers, the box that holds all your API keys has been a steady target since May, and you should be on 1.84.0 or later today.

The new entry is CVE-2026-40217. It lets someone with an admin key run code on the proxy server. That sounds narrow. In practice, on a machine whose whole job is to hold OpenAI, Anthropic and cloud credentials, it is not.

What the guardrail tester got wrong

LiteLLM is an open-source proxy from BerriAI that gives teams one OpenAI-style API in front of dozens of model providers, with key management, spend tracking and guardrails on top. One guardrail option lets you write your own check in Python. To help you debug it, the proxy offers a test endpoint, POST /guardrails/test_custom_code, that runs the code you send.

The problem was the sandbox around that code. Researchers at X41 D-Sec found in February that it worked by scanning the submitted source text for forbidden names. A text filter only sees what is literally written, so code that builds those names at runtime walks straight past it. From there an attacker can reach Python's unrestricted built-ins and run whatever they like inside the proxy process. In LiteLLM's default Docker image, that process runs as root.

X41's timeline is not flattering. It reported the issue on 13 February, chased the vendor through March, had an email bounce, and published on 8 April when its embargo ran out with no patch available. LiteLLM's own advisory followed in May. The fix replaced the hand-rolled filter with RestrictedPython, a library built for exactly this job.

There is one wrinkle to know about. The advisory's metadata lists 1.83.10 as patched, while its text says the fix landed in 1.83.11. Heise and several other write-ups use 1.83.11. Treat 1.83.11 as the floor, and since the other bugs below need a later release anyway, it is moot if you go to 1.84.0.

Why an admin-only bug still gets exploited

In a default setup you need a proxy admin credential to reach the endpoint. LiteLLM's maintainers scored it 5.9 for that reason, while the CVSS 3.1 score in public vulnerability databases is 8.8. CISA does not say who is exploiting it or how, and no public report yet describes the attacks.

The history of this product suggests a reason the admin requirement is a weak wall. Admin keys on gateways tend to be long-lived, shared across a team and pasted into scripts. And earlier this year LiteLLM shipped bugs that hand out access without any key at all.

The pattern is plain in CISA's catalog:

  • May: an SQL injection in the code that checks API keys, reachable by anyone who can send a request with a crafted Authorization header. CISA's entry warns it can expose the proxy's database and the credentials it manages.
  • June: command injection in two MCP test endpoints. Any valid key worked, including low-privilege internal ones. The Hacker News reported that Horizon3.ai chained it with a host-header bypass in the Starlette web framework to reach it with no key at all.
  • September: the MCP endpoint accepted any made-up Bearer token as a logged-in session.
  • November: the guardrail tester.

Nothing public ties this week's attacks to those earlier bugs, so do not read the list as one campaign. Read it as a description of the risk. A gateway that has leaked keys before is a gateway where an attacker may already hold an admin key, and an admin key plus this bug is root on the server.

Two of the four were test endpoints: features that exist to run code you hand them.

What to do this morning

  1. Find every LiteLLM you run. Check container images, Helm charts and requirements files, including the forgotten one a teammate set up for a hackathon. pip show litellm or the image tag tells you the version.
  2. Upgrade to 1.84.0 or later. That single step clears all four exploited bugs. If you pin Starlette yourself, make sure it is 1.0.1 or newer.
  3. If you cannot upgrade today, block the risky paths at your reverse proxy: POST /guardrails/test_custom_code, POST /mcp-rest/test/connection, POST /mcp-rest/test/tools/list, and the /mcp/ routes if you do not use MCP. That is the vendor's own advice.
  4. Take the admin UI off the internet. Put the management interface behind a VPN or an allowlist, and limit the master key to the people who need it. X41 also recommends running the container as a non-root user.
  5. Rotate what the proxy holds if you were on an affected version with any exposure: the master key, virtual keys, and every upstream provider key stored in its database or environment. Then look at provider billing for usage you do not recognise.

Federal agencies have until 2 December to fix this one. Nobody else has a deadline, which is not the same as having time.

The bigger picture

AI gateways have quietly become the most valuable box in a lot of companies: one service that holds every model key, sees every prompt and often talks to internal tools over MCP. LiteLLM is popular because it is quick to stand up, and that speed shows in features like code-running test endpoints that would never pass a design review at a bank. Whatever gateway you use, give it the treatment you give a password vault: private network, short-lived keys, fast upgrades and a log someone actually reads.
