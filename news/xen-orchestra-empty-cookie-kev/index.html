An empty cookie hands attackers your Xen Orchestra, and CISA wants it fixed by Saturday

CISA added ten exploited flaws to its catalog on 25 November, with most due over the US holiday weekend. Here is what the worst three do, which versions fix them, and what to check if you run Xen Orchestra, Juniper Session Smart or Mitel MiCollab.

CyberNovember 26, 20266 min read

If you run Xen Orchestra, the web console that manages XCP-ng virtualization hosts, an attacker who can reach it can log in as one of your users by sending a cookie that contains nothing but an empty pair of braces. CISA put that flaw on its Known Exploited Vulnerabilities list on 25 November, along with nine others, and gave US federal agencies until Saturday 28 November to fix most of them. That is a three-day clock running straight through Thanksgiving, and the bugs on it are the kind that hand over whole server rooms.

The batch covers four vendors: five flaws in Mitel MiCollab, three in Danfoss AK-SM 800A controllers, one in HPE Juniper Session Smart Conductor and Router, and one in Xen Orchestra. CISA's alert says only that each was added on evidence of active exploitation. The vendor records fill in the rest, and they are not equally alarming.

How a pair of braces became a login

The Xen Orchestra bug, CVE-2026-133469, is almost elegant in how little it asks of an attacker. The REST interface parses a cookie value that starts with j: as JSON. Send authenticationToken=j:{} and the server turns it into an empty object, then uses that object as a database filter. An empty filter matches everything, so the lookup returns the first stored token. If that token has not expired, you are now its owner. From there, a REST route that lists the user's own login tokens hands back reusable credentials.

Vates published its advisory, VSA-2026-062, on 10 November and said plainly that a threat actor was already using it. The CVE number only arrived on 23 November, which is why some trackers still list the flaw under its vendor ID alone. It is rated 9.8.

The fix is in Xen Orchestra 6.9.2 on the stable channel and 6.10.1 on the latest channel, which carry xo-server 5.211.2 and 5.213.1. Some early coverage named 6.9.1 and 6.10.0; Vates's own page says 6.9.2 and 6.10.1, so go by that.

The second half of the attack is not patched

Getting into the console was only the start. Vates says the same actor then abused a second weakness, VSA-2026-063, to break out of Xen Orchestra and onto the XCP-ng hosts underneath. Xen Orchestra talks to the hypervisor's API with pool-admin rights and passes VM import streams through without inspecting them. A user allowed to import a VM can therefore smuggle in configuration keys that should never be user-controlled, such as one that points a VM's serial console at a file on the host.

As of its last update on 10 November, Vates listed that fix as in progress, with no fixed version in either channel. Its interim advice is to strip the vm.import, sr/import:vm, network/action:create and network/action:update permissions from every account that does not strictly need them. The attacker in this campaign used an admin account, so trimming permissions narrows the problem rather than closing it.

A management console that can be fooled by an empty cookie should never have been reachable from the internet in the first place.

Vates says the same thing in drier words: keep Xen Orchestra on a dedicated management network. If you cannot do that today, it suggests blocking both the raw and URL-encoded forms of the empty-object cookie at a reverse proxy or web application firewall, while warning that pattern rules can be bypassed.

Checking whether you were already hit

Patching does not undo a compromise, and Vates notes the login bypass leaves nothing in the logs that would flag it. Its advisories list traces to hunt for instead:

  1. In Xen Orchestra, a running VM named pivot2.
  2. On XCP-ng hosts, VMs configured with hvm_serial: file.
  3. On hosts, the files /etc/cron.d/zz-ustar, /etc/cron.d/zz-ustar2, /.ustar5 and /.ustar6, and anything unexpected in /etc/ld.so.preload.
  4. Traffic to or from the IP addresses and Tor address in VSA-2026-062, including 91.211.251.112 on port 8001.

If you find any of them, Vates recommends rotating every password and secret the console held and reinstalling the affected machines rather than cleaning them.

Juniper and Mitel, the other two you should not leave

The Juniper flaw, CVE-2026-103406, sits in the AutomatedProvisioner service of Session Smart Conductor, the box that manages a fleet of SD-WAN routers. A remote attacker with no credentials can run commands as root by sending a crafted Salt minion ID. Salt is the configuration management system the product uses to talk to its routers, so the bug lives on the path that is supposed to be trusted. It is rated 9.8.

Juniper disclosed and fixed it on 28 October in releases 7.0.5, 7.1.7 and 7.2.3, with no workaround. Its record now says at least one malicious exploitation has been reported to Juniper's security team. Anyone who skipped the October update has been exposed for a month.

Mitel's five MiCollab flaws all work without authentication. The two that matter most are a blind command injection rated 10.0 (CVE-2026-133323) and an XML injection rated 9.0 (CVE-2026-133303). Mitel's advisory, first issued on 16 November and revised on 24 November, covers MiCollab 10.3.0.18 and earlier. The fix is a patch for 10.3.0.18, described in Mitel knowledge base article KB000129195, or a move to a later release. Mitel's own page does not say the flaws are exploited; CISA's listing is the evidence. If you cannot patch, Mitel suggests cutting external access to the AWV conferencing component.

The three Danfoss bugs are older: two from 2023 and one from 2025, in controllers that run supermarket refrigeration and building systems. Their appearance on the list means someone is using them now. Firmware fixes have been out for a while, but sources disagree on exactly which release covers each CVE, so check Danfoss's own advisory for your model.

The bigger picture

Three of these ten bugs live in software whose whole job is to manage other machines: a hypervisor console, an SD-WAN controller and a unified communications server. Owning one means owning everything it manages, which is why attackers keep coming back to them and why they keep turning up on CISA's list. The Xen Orchestra case adds a sting: the fix for the way in shipped within days, while the fix for the way down to the hosts had not yet shipped at Vates's last update. Patch what you can this weekend, and take the consoles off the open internet for good.
