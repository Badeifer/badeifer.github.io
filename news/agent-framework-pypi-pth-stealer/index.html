The Dispatch

Microsoft's agent-framework shipped a credential stealer that runs even if you never import it

Two hijacked releases of Microsoft's Python agent library sat on PyPI for under an hour and planted a startup hook that grabs Azure, CI and AI keys. Here is how the trick works, how to check your machines without setting it off, and what to rotate.

CyberNovember 18, 20265 min read

Someone published two poisoned versions of Microsoft's agent-framework package to PyPI on Tuesday evening, and both carried a credential stealer that fires every time Python starts. If any laptop, container or build agent of yours ran pip install agent-framework without a pinned version between 20:35 and roughly 21:30 UTC on 17 November, treat every secret it could reach as stolen.

The package is Microsoft's official Python library for building AI agents, the successor to Semantic Kernel and AutoGen, and it pulls around 190,000 downloads a month. The bad releases are 1.26.1 and 1.26.2. PyPI has removed both, and 1.26.0 from 12 November is once again the latest version.

A hook that does not wait for an import

The clever part is where the code lives. Each malicious wheel dropped a small .pth file into site-packages. Python reads those files when the interpreter boots, mostly to extend the import path, but any line that starts with import is executed. That turns them into a startup hook for every Python process in the environment.

So the stealer did not need you to use the library. Running a test suite, a linter, a notebook or an unrelated script in the same virtual environment was enough. Version 1.26.1 used agent_framework_meta.pth. When 1.26.2 arrived 33 minutes later, the payload had moved to af_runtime_diag.pth and a new top-level module, and the original agent_framework_meta/__init__.py was restored byte for byte to the clean 1.26.0 copy. Endor Labs points out that anyone diffing only the library's own folder would have seen nothing.

Both wheels also pinned the genuine agent-framework-core 1.26.0, so applications installed and ran normally. Nothing broke, which is the point.

What it went looking for

The target list reads like a CI pipeline's pockets. According to Wiz and Endor Labs, the collector grabbed environment variables with names containing words like TOKEN, SECRET, KEY, AZURE, AWS, GITHUB and OPENAI, and it read the environments of other running processes through /proc. It swept dozens of credential files: Azure CLI tokens, .npmrc, pip.conf, .netrc, .git-credentials, Docker and Hugging Face configs, Azure DevOps agent credentials, plus .env and JSON files under /app and /workspace.

On cloud machines it asked the Azure metadata service for managed identity tokens for 12 resources. Inside Azure DevOps it requested a pipeline OIDC token, and 1.26.2 added the same for GitHub Actions jobs that have id-token: write, the setting that lets a workflow log in to Azure without a stored secret. Everything went out in one compressed POST to a throwaway webhook.site address.

Wiz noticed something the attacker probably did not intend: the free webhook tier caps out at 100 requests, and the operator's own tooling reported progress to the same URL. By Wiz's count on Wednesday, the endpoint logged 50 requests, of which 17 carried real victim data from three distinct sources. Most of the rest were scanners and sandboxes. That is a small blast radius, but it only counts what reached that one URL, and stolen cloud tokens can stay valid for up to a day.

How it got published is still open

Nobody has explained how an outsider pushed to Microsoft's package. Neither release has a matching tag in the GitHub repository, neither shipped a source archive the way real releases do, and PyPI shows no provenance attestation for them. Wiz says the attacker appears to have obtained a certificate and private key used by Microsoft's internal release signing service, and that a first upload attempt from AWS was blocked by IP filtering before a second one from Microsoft-owned address space went through. SecurityWeek reports that SafeDep spotted a PyPI maintainer account created the same day with rights to the package; its role is unconfirmed.

Microsoft has said little in public. A maintainer told users on GitHub that the releases were pulled and an investigation was under way, and the repository itself was offline on Wednesday. This is also the second Microsoft PyPI package hijacked this year, after three trojanised durabletask releases in May. No researcher has linked the two.

Check and clean up

The first rule here is odd but important: do not start the suspect Python to find out.

Every interpreter launch in an infected environment runs the stealer again. Work from the outside.

  1. Search your records. Grep lockfiles, requirements*.txt, CI logs, dependency caches and container images built after 20:35 UTC on 17 November for agent-framework 1.26.1 or 1.26.2.
  2. Look for the files. In each environment's site-packages, check for agent_framework_meta.pth, agent_framework_meta/_telemetry.py, af_runtime_diag.pth and af_runtime_diag.py. Use find or your file manager, not Python.
  3. Rebuild, do not repair. Throw away affected virtual environments and images and rebuild from a pin: agent-framework==1.26.0, ideally with --require-hashes. Block 1.26.1 and 1.26.2 in any package proxy.
  4. Rotate everything reachable. Azure service principals and CLI sessions, Azure DevOps PATs and service connections, GitHub tokens and federated credentials, npm, PyPI, NuGet, Docker and Hugging Face tokens, and model provider keys such as OpenAI's.
  5. Read the logs. Search proxy and DNS logs for webhook.site and the user agents af-runtime-diagnostics/1 and runtime-diagnostics/1, and review Azure sign-in logs for managed identities used from affected hosts since the install.

If your builds use a lockfile with hashes and nobody refreshed it on Tuesday night, you were almost certainly fine.

The bigger picture

Agent libraries are a rich target because of what sits next to them. A machine that builds AI agents tends to hold cloud identities, model API keys and the CI tokens that deploy everything else. The .pth trick is not new, but it fits this moment: a package you never import can still own your interpreter. Pinning with hashes and waiting a day before taking fresh releases would have stopped this one cold, and that is cheaper than any rotation weekend.
